# tools/

Maintenance tooling for the **OS.Sensitivity.III** warehouse.

## `validate_shapes.py`

Validates the root [`shapes.json`](../shapes.json) descriptor that the SLeeLa
OS Creator (`SLOSSensitivitySource` / `SLOSSensitivityFetch`) resolves to fetch
OS-grade C/C++ source for a chosen shape.

```sh
python3 tools/validate_shapes.py
```

It runs two checks, both required for the descriptor to be trusted:

1. **Structure** — `shapes.json` conforms to the JSON Schema
   [`schemas/shapes-1.0.json`](../schemas/shapes-1.0.json). If the optional
   `jsonschema` package is installed it is used for a full Draft 2020-12
   validation; otherwise a built-in standard-library subset validator runs, so
   the tool works with **no third-party dependencies**.
2. **Resolution** — every repo-relative path declared in `shapes.json`
   (shape `root`, each component `path`, and every `sources` / `compliance` /
   `licenses` / `build` reference) **exists on disk**. This is the property the
   OSCreator runnable depends on: a chosen shape must resolve deterministically
   to real source before it is fetched.

Exit status is `0` only when both checks pass; any problem prints its exact
JSON location and exits non-zero.

### Options

| Flag | Default | Meaning |
|---|---|---|
| `--shapes` | `shapes.json` | descriptor to validate |
| `--schema` | `schemas/shapes-1.0.json` | schema to validate against |
| `--root` | repo root | base directory for resolving declared paths |

## `validate_provenance.py`

Content checks that complement `validate_shapes.py`: once a shape resolves, is
its **provenance stated** and is its **build entry point real**?

```sh
python3 tools/validate_provenance.py
```

Two layers:

1. **Provenance / compliance** — every referenced doc (`compliance`,
   `licenses`, `sources`, `build`, and each component `sources`) exists and is
   non-empty; a component that declares an `upstream` also declares a
   `license` (provenance is never half-stated); clean-room shapes
   (`notMicrosoftWindows` / `notAppleMacOS` / `cleanRoom`) carry both a
   `COMPLIANCE.md` and a `LICENSES.md`; and each `SOURCES.md` mentions the
   component's pinned ref or upstream (reported as a warning if not).
2. **Build-entry smoke** — for every component with a `buildEntry`, the file(s)
   that entry point needs are present at the component path
   (`make` → `Makefile`, `./configure` → `configure`, `cmake` →
   `CMakeLists.txt`, `./configure.sh` → `configure.sh`, …). It understands
   autotools/cmake ordering: a `make`/`ninja` step preceded by a satisfied
   configure step (e.g. `./configure && make`) is accepted, since the
   `Makefile`/`build.ninja` is generated by that step. **No build is run** —
   this only proves the entry point is not dangling.

Errors fail the run (exit non-zero); warnings are printed but do not fail.
Standard-library only, no network.

## CI

Both validators run automatically on every push and pull request via
[`.github/workflows/validate-shapes.yml`](../.github/workflows/validate-shapes.yml),
so a descriptor that points at a missing/malformed path, states provenance only
halfway, or names a dangling build entry point cannot land on `main`.
